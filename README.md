
# Structured Development Workflow

一个面向 Codex 的开发规划与文档治理 Skill。

它负责读取项目上下文、澄清需求、编写设计文档、分析影响范围、拆分开发任务、建议执行角色并生成交接包，但不负责编写业务代码、运行应用测试、提交代码或部署系统。

> 本项目是社区维护的 Codex Skill，不代表 OpenAI 官方产品。

## 核心定位

在普通 AI 开发流程中，用户经常只提供几句话，AI 就直接开始修改代码，容易出现以下问题：

- 没有充分理解项目背景。
- 需求、范围和验收标准不明确。
- 忽略现有架构和项目惯例。
- API、数据模型和实现相互脱节。
- 开发任务难以拆分和分配。
- 文档在开发完成后才根据记忆补写。
- 实际实现与原始设计逐渐偏离。

本 Skill 将 Codex 定位为更高一层的“开发规划与文档治理者”：

```text
读取项目上下文
→ 澄清需求
→ 判断任务等级
→ 盘点已有文档
→ 编写产品与技术设计
→ 分析影响与风险
→ 提出文档变更计划
→ 等待用户批准
→ 写入规划文档
→ 拆分任务与建议角色
→ 生成执行交接包
→ 验证文档
→ 等待用户验收
```

实际编码、测试、迁移、提交和部署应交给开发者或其他执行 Agent。

## 主要能力

### 项目上下文调研

以只读方式检查：

- `AGENTS.md`、README 和已有开发文档。
- 项目目录、相关代码和测试。
- 路由、模块、配置和依赖清单。
- 数据库 Schema、迁移记录和数据模型。
- OpenAPI、Proto、Schema 等接口契约。
- Git 状态、历史和 diff。
- 已有架构设计、决策记录和任务计划。

现有代码、配置、测试、文档和用户明确确认的决策是主要事实来源。

### 需求澄清

在生成设计前明确：

- 背景与问题。
- 目标和非目标。
- 用户与使用角色。
- 核心使用场景。
- 业务规则。
- 异常与边界情况。
- 兼容性和安全约束。
- 可验证的验收标准。
- 仍需确认的假设。

Skill 会优先从仓库寻找答案，只询问无法可靠推断且会影响产品、架构、数据、接口或任务设计的问题。

### Level 1–3 分级


| 等级    | 适用场景                                   | 主要产物                                   |
| --------- | -------------------------------------------- | -------------------------------------------- |
| Level 1 | 文案、样式、小范围明确修改                 | 单份变更说明、任务与验收清单               |
| Level 2 | 普通功能、多模块调整、新页面或兼容 API     | 轻量 PRD、流程、技术设计、影响分析、任务包 |
| Level 3 | 新项目、核心架构、权限、支付、重大数据迁移 | 完整设计文档链、路线图、任务分配和交接包   |

Level 3 的完整适用文档链为：

```text
需求澄清
→ 一页 PRD
→ 产品与异常流程
→ 页面与交互草图
→ 技术架构
→ 数据模型
→ API 契约
→ 影响与风险
→ 实施路线图
→ 任务分配
→ 测试与验收计划
→ 执行交接包
```

只生成与任务真正相关的文档。例如，纯后端任务不会强制创建页面草图，没有数据变化时不会虚构数据库迁移设计。

### 文档生命周期管理

Skill 不只是生成新文档，还会：

- 盘点已有文档和引用关系。
- 判断权威文档来源。
- 更新已有文档，避免重复创建。
- 合并重复或冲突内容。
- 标记过时和已废弃文档。
- 维护任务、决策和验收之间的追踪关系。
- 根据外部开发结果更新文档状态。
- 规划归档或删除操作。
- 检查文档链接和引用完整性。

任何文档写入前，Skill 都会先输出文档变更计划并等待用户批准。

### 任务拆分与角色建议

每个任务卡包含：

- 任务编号、名称和目标。
- 推荐执行角色。
- 负责人或 `Unassigned`。
- 前置依赖和并行批次。
- 阻塞条件。
- 输入材料和关联设计文档。
- 允许修改的范围。
- 禁止修改的范围。
- 实施步骤。
- 预期产物。
- 完成定义。
- 测试和验收要求。
- 回滚要求。
- 文档同步要求。
- 后续交接对象。

Skill 可以生成可直接交给开发者或执行 Agent 的任务提示词，但不会自动启动、委派、协调或监督执行者。

## 职责边界

### 允许执行

- 只读检查代码、配置、测试、Git 历史和 diff。
- 编写和更新 Markdown 等人类可读开发文档。
- 编写 PRD、流程、页面草图和技术架构。
- 设计数据模型、迁移策略和回滚方案。
- 编写 API 设计和契约说明。
- 分析影响、风险和未知项。
- 生成实施路线图、任务卡和执行交接包。
- 设计测试计划和验收标准。
- 根据外部实施结果更新文档和任务状态。
- 运行文档链接、格式、引用和语法检查。
- 在单独批准后维护 OpenAPI、Proto、Schema 等机器可读契约。

### 禁止执行

- 编写或修改业务代码。
- 编写或修改测试代码。
- 修改构建配置、依赖、锁文件或迁移脚本。
- 安装或升级依赖。
- 运行应用测试、构建、Lint、类型检查或迁移。
- 运行代码生成。
- 修复开发者提交的代码。
- 启动或管理其他开发 Agent。
- 执行 `git add`、提交、推送、建分支或修改历史。
- 创建 PR、合并、发布或部署。
- 操作生产环境或数据库。

完成规划和文档不代表业务功能已经实现。

## 审批门禁

### 文档写入审批

在修改项目文档前，Skill 会先输出：

```text
新增文档
更新文档
合并文档
归档文档
拟删除文档
明确不修改的文档
目标路径
信息来源
引用影响
验证方式
```

用户批准后，Skill 才会实际写入文档。

### 机器契约审批

修改以下机器可读契约前需要单独批准：

- OpenAPI。
- Proto。
- JSON Schema。
- YAML Schema。
- 其他可能驱动代码生成或影响外部消费者的规范。

Skill 只修改获批的契约文件并进行静态校验，不运行代码生成，不修改消费者代码。

### 删除审批

默认处理顺序：

```text
更新权威文档
→ 合并重复内容
→ 标记 Superseded
→ 移入已有归档区
→ 永久删除
```

永久删除前必须：

1. 检查入站引用。
2. 提供替代或归档方案。
3. 保留必要的历史和决策记录。
4. 获得单独明确批准。

## 推荐使用流程

### 阶段一：开发前规划

```text
使用 $structured-development-workflow 规划以下需求：

需求：
给现有系统增加用户登录功能。

目标：
支持邮箱和密码登录。

约束：
继续使用现有用户表，不接入第三方登录。

非目标：
本阶段不做手机号登录和多因素认证。

验收预期：
用户登录后可以保持会话，错误密码有明确提示。

请先读取项目和已有文档，完成需求澄清、Level 分级和文档盘点，
然后提出文档变更计划。暂时不要修改文档，也不要编写代码。
```

### 阶段二：批准文档并生成交接包

```text
确认文档变更计划。

请按照批准的范围写入文档，并完成：
1. 产品与技术设计。
2. 影响和风险分析。
3. 实施路线图。
4. 任务拆分和依赖关系。
5. 推荐执行角色。
6. 可直接交给开发者或执行 Agent 的任务提示词。

不要启动执行 Agent，不要编写业务代码。
```

### 阶段三：开发过程同步

```text
使用 $structured-development-workflow 进行进度同步。

当前执行结果：
- TASK-API-01 已完成。
- 开发者调整了 API 路径。
- 单元测试 18 项通过，2 项失败。
- 失败原因由执行者报告为测试数据库缺少索引。
- 附上测试报告和 diff 摘要。

请区分：
- 已确认事实。
- 执行方报告。
- 有证据支持的结果。
- 仍待验证的内容。

更新受影响的任务状态、风险、API 设计和后续计划。
先输出文档变更计划，等待批准后再写入。
```

### 阶段四：开发完成后同步

```text
使用 $structured-development-workflow 完成最终文档同步。

开发结果：
- TASK-API-01、TASK-FE-01 和 TASK-QA-01 已完成。
- 自动测试和人工验收结果已附上。
- 登录失败次数功能延期。
- API 契约与最终实现一致。
- 附上最终 diff 摘要。

请更新：
1. 任务状态。
2. 验收记录。
3. API 和架构文档。
4. 已知限制和延期事项。
5. 下一阶段路线图和任务建议。

不要把缺少证据的内容标记为已验证。
```

## 什么时候使用

推荐在以下节点使用：

1. 新需求准备开始。
2. 需要编写 PRD、架构、数据或 API 设计。
3. 需要把方案拆成开发任务。
4. 需要生成多人或多 Agent 分工方案。
5. 需求、架构、数据或接口发生实质变化。
6. 一个开发阶段或任务批次完成。
7. 开发者返回测试结果和 diff 摘要。
8. 功能开发和人工验收完成。
9. 需要同步文档并规划下一阶段。
10. 需要合并、归档或清理过时文档。

不应隐式用于：

- 直接实现功能。
- 直接修复 Bug。
- 直接重构代码。
- 普通知识问答。
- 单纯解释代码。
- 只读代码审查。
- 翻译或总结普通文本。

如果显式调用 `$structured-development-workflow`，即使请求中包含“实现”，它也只会生成规划、文档和执行交接包，不会进入编码阶段。

## 安装

### 使用 Skill Installer

在 Codex 中输入：

```text
使用 $skill-installer 从以下 GitHub 地址安装 structured-development-workflow：

https://github.com/<your-username>/<repository>/tree/main/skills/structured-development-workflow
```

请将 `<your-username>` 和 `<repository>` 替换为实际地址。

### 仓库级安装

将 Skill 复制到项目仓库：

```text
<repository>/
└── .agents/
    └── skills/
        └── structured-development-workflow/
            ├── SKILL.md
            ├── agents/
            ├── evals/
            └── references/
```

### 用户级安装

将 Skill 文件夹复制到：

```text
$HOME/.agents/skills/structured-development-workflow/
```

Codex 通常会自动检测 Skill 变化。如果没有显示，请新建任务或重启 Codex。

## 调用方式

推荐显式调用：

```text
使用 $structured-development-workflow 为这个功能编写 PRD、技术设计并拆分执行任务。
```

也支持符合描述的隐式调用，例如：

```text
请分析当前项目，为权限系统整理架构设计、数据模型和任务交接包。
```

## 验证

当前版本已经完成：

- 官方 `quick_validate.py` 验证。
- Front matter 检查。
- 引用路径完整性检查。
- 职责边界静态检查。
- 直接编码请求反例检查。
- 显式调用停止在代码前的行为检查。
- 文档审批、契约审批和删除审批检查。
- 22 条触发测试，包括 15 条正例和 7 条反例。
- 本机路径、密钥和凭据扫描。

## 限制

- Skill 不会自动保证规划与最终实现一致，需要在开发过程中提供真实执行结果。
- Skill 不会运行应用测试或验证业务代码。
- 外部开发者提供的结果会标记为执行方报告，除非附有可核对证据。
- Skill 不会自动启动其他 Agent。
- Skill 不会提交、推送、合并或部署。
- 机器契约修改可能影响代码生成或外部消费者，因此需要额外审批。
- 触发测试目前是静态提示词矩阵，不是完整的真实模型批量评测。
