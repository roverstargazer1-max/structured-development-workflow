## 拆分原则

把路线图拆成可由单一执行角色独立完成和验收的任务：

- 一个任务只承担一个清晰目标，避免把前端、后端、数据迁移和验收混成不可追踪的大任务。
- 任务输入必须引用已批准的需求或设计，不让执行者重新决定产品意图。
- 写明允许和禁止修改范围，防止顺手重构。
- 给出完成定义和可观察验收条件，不使用“完成相关开发”之类描述。
- 把未知项拆成调研或验证任务，不让执行者用猜测补齐契约。
- 把文档同步列为对应任务产物或独立任务。

## 依赖与并行批次

用任务编号表达依赖，生成并行批次：

```text
Wave 0：决策、契约和环境确认
Wave 1：无相互依赖的基础任务
Wave 2：依赖 Wave 1 产物的集成任务
Wave 3：验证、迁移、文档同步和验收
```

每项任务标记：

- `Depends on`：必须完成的任务。
- `Blocks`：被当前任务阻塞的任务。
- `Parallel with`：可安全并行的任务。
- `Blocking condition`：外部权限、数据、设计或环境条件。

不要仅按任务编号推断执行顺序。

## 任务卡模板

```markdown
## TASK-[编号]：[任务名称]

- 状态：Planned / Ready / In Progress / Blocked / Review / Accepted / Deferred
- 推荐执行角色：[角色]
- 负责人：Unassigned 或明确人员
- 所属批次：Wave [N]
- 前置依赖：
- 阻塞条件：

### 目标

### 输入材料
- PRD/设计/契约/决策：

### 允许修改范围
- 模块或目录：

### 禁止修改范围
- 明确排除：

### 执行步骤
1. [由执行者完成的步骤]

### 预期产物
- 代码、配置、迁移、测试或文档产物：

### 完成定义
- [可判断的完成条件]

### 测试与验收要求
- 自动检查：
- 手工验收：
- 失败路径：

### 回滚要求
- 回滚触发条件与恢复目标：

### 文档同步要求
- 完成后更新：

### 交接对象
- 下一角色或任务：
```

任务卡可以描述执行者应修改代码或运行测试，但必须使用“执行者应……”的交接语义，不能指示当前 Skill 亲自实施。

## 角色建议

根据项目实际角色选择，例如产品、UX、前端、后端、数据、平台/DevOps、安全、QA、技术写作或评审人。没有人员信息时：

- 填写 `负责人：Unassigned`。
- 填写具体的推荐角色及所需能力。
- 不虚构姓名、团队或可用性。
- 不自动创建子 Agent、线程、Issue 或外部任务。

## 执行 Agent 交接提示词

为每个任务生成可独立使用的提示词：

```text
你负责执行 TASK-[编号]：[名称]。

目标：...
事实与批准决策：...
输入文档：...
允许修改：...
禁止修改：...
依赖与前置条件：...
预期产物：...
必须运行的测试：...
验收标准：...
完成后请返回：实际修改、测试结果、diff 摘要、未决问题和需要更新的文档。

不得重新解释产品范围；如发现会改变架构、数据、API、安全或验收标准的问题，请暂停并返回规划者确认。
```

交接提示词只是产物。本 Skill 不得发送任务、启动、委派、协调或监督任何执行 Agent；需要执行时，由用户在本 Skill 之外选择并授权执行者。

## 汇总矩阵

```markdown
| 任务 | 角色 | 负责人 | Wave | Depends on | 状态 | 主要产物 | 验收人/角色 |
|---|---|---|---:|---|---|---|---|
```

检查每个需求、设计决策和风险至少关联一个任务或明确标记为非执行项；检查每个任务都能追溯到已批准文档。
