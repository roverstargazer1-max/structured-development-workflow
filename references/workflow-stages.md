# 文档规划工作流阶段

## 目录

- 阶段输入输出
- 文档就绪检查
- 需求澄清
- 文档审批
- 进度同步
- 失败与冲突
- 阶段沟通

## 阶段输入输出

| 状态 | 必要活动 | 退出条件 |
|---|---|---|
| `DISCOVER` | 只读定位仓库、规则、代码、配置和权威文档 | 能描述当前实现与约束 |
| `CLARIFY` | 核对通用信息和文档类型必要输入 | 所有阻塞项已由仓库事实或用户明确回答 |
| `WAITING_FOR_REQUIRED_CONTEXT` | 输出事实、缺口、阻塞原因和 1-3 个问题后停止下游推进 | 用户补充信息后返回 `CLARIFY` 重新检查 |
| `SIZE` | 按风险和复杂度判定 Level 1-3 | 文档深度已说明 |
| `DOCUMENT_AUDIT` | 盘点文档、职责、引用、重复和过时项 | 已识别权威来源和文档缺口 |
| `DESIGN` | 生成最少充分的产品和技术设计草案 | 决策可转化为文档和任务 |
| `IMPACT_ANALYSIS` | 区分事实、影响、风险、假设和未知项 | 范围与风险可追踪 |
| `DOCUMENT_CHANGE_PLAN` | 形成文件级文档包清单和引用关系 | 每项有 ID、职责、路径、操作、权威范围、上下游、来源和验证方式 |
| `WAITING_FOR_DOCUMENT_APPROVAL` | 暂停所有项目文档写入 | 用户明确批准当前文档计划 |
| `WRITE_DOCUMENTS` | 逐项写入批准的文档并维护索引；契约变更另行确认 | 清单内产物均已落盘，索引和元数据同步 |
| `TASK_DECOMPOSITION` | 形成可独立执行和验收的任务卡 | 每项任务有独立入口、上游输入、依赖、范围和完成定义 |
| `ASSIGNMENT_AND_HANDOFF` | 在任务索引记录角色、负责人、Wave 和状态并生成交接提示词 | 每项任务可独立交给执行者，未知负责人标为 Unassigned |
| `DOCUMENT_VALIDATION` | 校验文件、索引、ID、链接和追踪关系 | 追踪不变量闭合，结果已记录，问题已修正或披露 |
| `WAITING_FOR_USER_ACCEPTANCE` | 汇总文档与交接产物并暂停 | 用户接受或提出文档修改意见 |
| `DONE` | 结束文档工作 | 不进入编码或 Git 流程 |

## 文档就绪检查

先读取仓库中可发现的事实，再检查以下通用必要信息：

- 文档目的、预期受众和使用场景。
- 真实背景、当前问题和现状证据。
- 目标、非目标和范围边界。
- 用户、角色及其权限或职责差异。
- 已知约束、关键业务规则和已批准决策。
- 可观察、可验证的验收标准。
- 权威资料来源；更新、合并或归档时还要确认目标文档及其权威范围。

按产物追加检查：

| 产物 | 开始编写前必须确认 |
|---|---|
| 页面、流程或交互草图 | 涉及页面、目标角色、主流程、关键分支以及空/加载/成功/错误等适用状态 |
| API 或事件契约 | 消费者、输入输出语义、认证授权、错误与兼容要求，以及权威契约位置 |
| 数据模型或迁移设计 | 核心实体、数据来源与所有权、生命周期、隐私/保留要求，以及适用的迁移和回滚约束 |
| 技术架构 | 当前实现证据、目标能力、系统边界、关键质量约束和不可改变的既有决策 |
| 任务拆分与交接 | 已批准的需求和设计边界、依赖关系、预期产物、完成定义及测试/验收要求 |
| 进度或结果同步 | 报告内容、来源、时间、证据状态，以及需要更新的权威文档或任务 |

缺失信息只要可能改变需求含义、架构、数据、接口、安全、验收、任务边界或文档权威性，就属于阻塞项。标题、排版、编号、仓库已有目录规则等不改变需求含义的事项可以采用默认值，但必须说明依据。负责人未知时使用 `Unassigned` 和推荐角色，不虚构人员、团队或可用性。

未通过检查时禁止：

- 判定 Level 1-3。
- 输出文档目录、结构草案、正文草案、设计、影响分析或文档变更计划。
- 拆分任务、分配角色或生成执行交接包。
- 用 `Assumption`、`Unknown`、`TBD`、模板占位符或“先按高等级处理”替代用户确认。

仅当用户明确把交付物限定为问题清单、调研提纲、决策待办或纯目录建议时，才可输出对应辅助材料，并明确标注“不是正式需求或设计文档”。

## 需求澄清

先从代码和文档寻找答案，不询问只读检查可以可靠获得的事实。每轮只提出 1-3 个最高优先级的阻塞问题，并在用户回答后重新执行完整就绪检查。

```markdown
## 需要确认的问题

### 阻塞性问题
1. 问题：
   - 已知事实：
   - 缺失信息：
   - 必须确认的原因：
   - 影响的文档或决策：
   - 可选方案（仅在有事实依据时）：
   - 推荐方案及依据（如适用）：

### 可采用的非实质默认值
1. 当前默认值：
   - 依据：
   - 为什么不改变需求含义：
```

没有事实依据时直接询问所需背景，不编造选项诱导用户选择。用户暂时无法回答时，只提供以下出口：指出需要补充的材料、建议缩小正式文档范围，或建议把本轮交付改为问题清单/调研提纲/决策待办；不得继续编写完整 PRD 或正式设计。

## 文档审批

通过文档就绪检查后，才可进入文档审批流程。在批准前只在对话中展示文件级文档包清单、摘要、变更矩阵和关键草案，不写入项目文件。清单逐项列出文档 ID、职责、路径、操作、权威范围、上下游关系和验证方式。批准必须针对当前版本的文件清单；用户最初说“帮我写文档”不自动等于批准未知的文件、删除、归档或契约修改。

若批准后发现需要新增文件、改变权威规范、移动文档或扩大契约范围，暂停相关写入并更新计划。普通措辞修正和不改变结构的格式调整可继续，但在交付摘要中披露。

## 进度同步

接受以下输入：开发者状态、测试报告、diff 摘要、验收反馈、迁移或发布结果。执行：

1. 标明来源、时间和可信度，不把外部报告改写成本 Skill 亲自验证。
2. 将任务状态更新为 `Planned`、`Ready`、`In Progress`、`Blocked`、`Review`、`Accepted` 或 `Deferred`。
3. 更新受影响的任务卡、任务索引、追踪矩阵、决策、风险、验收记录和文档索引。
4. 先输出文档变更计划，获得批准后再落盘。
5. 不运行应用检查，不修复实现，不启动执行者。

## 失败与冲突

- 文档互相矛盾：以代码、权威契约和最新明确决策为证据，列出冲突，不擅自选择产品意图。
- 契约校验失败：修正文档语法或报告设计冲突；不得运行代码生成或修改消费者代码。
- 外部结果缺少证据：标记“执行方报告，未独立验证”，保留待验证项。
- 真实背景或关键决策不足：进入 `WAITING_FOR_REQUIRED_CONTEXT`，不得以草案、假设或较高 Level 继续推进。
- 文档归属不明：停止覆盖，说明候选权威来源和合并方案。
- 删除存在引用：默认改为废弃标记或归档，等待单独批准。

## 阶段沟通

每次等待批准时说明当前状态、已完成草案、是否写入任何文件、需要批准的文件级操作，以及批准后将写哪些文档。完成时只提供文档与任务入口、状态和验证结果，不重复粘贴正文，并明确“文档与交接完成，不代表功能已实现”。
